# Seven-day project activity

The `/tickets` list hides successfully loaded projects with no recorded ticket changes in the seven IST dates ending today. Missing activity and legacy UTC-only history count as no recorded IST activity. Header ticket totals include only visible, successfully loaded projects. Loading and failed summaries remain visible so progress and retry controls stay available. Projects remain accessible from the sidebar and direct links; live summary updates and the existing date refresh automatically update list visibility. If all projects are inactive, the list shows “No project activity in the last 7 days.”

Status counts are a separate compact vertical bar chart: Backlog (green), Todo (pink), and In Review (yellow), using the same pastel fills as the status legend, fine colored edges, and no gray background tracks. The slim bars touch edge-to-edge and have no visible numbers at rest. Hover, focus, or tap a bar to see its status and exact count; Escape dismisses the tooltip. All projects share one linear height scale: the largest Backlog, Todo, or In Review count among successfully loaded projects sets the maximum. Equal counts have equal heights across rows, and all rows rescale together when that maximum changes. Loading or failed summaries do not affect the scale. Zero counts have no filled bar, but a one-pixel colored baseline keeps the chart and its hover targets discoverable (including all-zero projects). This marker does not contribute to the height scale. Unavailable counts show dashed tracks and a dash rather than zero. Status bars do not represent daily activity.

The `/tickets` list shows a thin green activity sparkline, inspired by GitHub's repository list. It plots seven daily counts, oldest first and today last, with straight segments (no fabricated intermediate samples). All loaded projects share one linear daily-activity scale, separate from the status-count scale. Open the graph by click, tap, or keyboard for exact daily counts. Dates use Indian Standard Time (Asia/Kolkata, UTC+05:30) so different clients share the same buckets, rolling over at midnight IST. The row shows only the sparkline, with no axes or visible period label; period and timezone remain available in the accessible label and expanded breakdown. The view refreshes its date on focus and once a minute.

Each successfully persisted ticket creation, edit (including estimates), move, or deletion contributes one change. Reads, unchanged saves, column management, comments, and imports do not create activity. Deletion recovery records the change once when deletion completes. Failed writes cannot leave an activity-only update.

History is a bounded `activity: { timeZone: 'Asia/Kolkata', throughDay, counts }` record with seven nonnegative integer counts. Local boards store it alongside cards in the same write. Firestore stores it on the board document in the same revision transaction as the ticket change; summary reads require no additional collections. Old documents without activity remain valid. Imports/exports preserve recorded history when present, without synthesizing events.

A flat muted line means no **recorded** changes, not a reconstructed historical claim. There is no backfill. Legacy UTC aggregates (records without `timeZone`) remain readable but are not displayed as IST counts: without event timestamps they cannot be accurately converted. The next recorded change starts a fresh IST window. Loading or failed summaries use a dashed line and an unavailable explanation instead of showing zero activity. When the activity component is shown outside the filtered list, an all-zero week remains a visible solid baseline; no minimum nonzero activity is invented.

## Deployment

Deploy the updated Firestore rules before deploying the frontend. The rules now permit and validate optional activity records; old rules reject writes containing this field. Clients need the updated board schema to read documents containing activity.
